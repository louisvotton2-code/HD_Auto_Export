# v2.0.0 运维验收与切换

本页供生产切换前验收、切换和回退使用。发布依据为用户验收过的同版组合、独立审查和 GitHub 必需检查。用签发的 Git 标签提交、构建树、镜像摘要、迁移账本和实际服务身份核对目标。在此之前检查生产仅限低频只读，压力验证使用隔离环境。

## 本地联调和承载

- 用 `127.0.0.1:3363` 同源接入官网、后台和 API。记录三端实际进程、版本、数据配置和入口验证。匿名后台访问应为 401，统计事件走官网同源入口。分别验证主动联系计数、经同意的浏览器会话、网关 HTML 文档汇总。测试车、统计、同步和供应商请求使用本地样本与合成供应商。
- 按相同 CPU、内存、进程资源配额和约 50 万条数据比较候选。分别记录冷缓存、热缓存、同步并行和缓存故障。20 并发的目录／筛选分别检查成功延迟 P95 ≤800 ms 和错误率 <1%。单列 429、5xx、连接失败、统计写入和丢弃、数据库等待和内存。50／100 并发用于标记瓶颈。真实生产只做有界冒烟。
- 验收俄罗斯语手机目录时用同网络、设备和相同操作跑三次，记录品牌检索可用时间中位数和失败样本。上线后另按真实用户样本报告 P75。

## 容量、恢复和观测

- 每次切换前核对当前准入、当前清单有效缺口、剩余席位和近期尚未准入的有效上游身份。将预计 24 小时席位需求和可用名额并列，注明撤回、别名、活跃快照及待处理事件造成的偏差。观察真实 CSV 创建、校验、暂存及扫完时间，另核对最新增量游标和按需访问标记。定时计划不能代替实际触发记录。
- 同一窗口分别核对准入上限、供应商配额或限流、上游未查到和其他失败。把已触顶时落为 `SYNC_LISTING_LIMIT` 的事件计入待清单对账的拒绝样本。用新一代已经校验的 CSV 和现行撤回、别名规则算实际缺口，再用第一方备份成本及实盘容量出据，按准入审批入口放行。本轮不改写旧事件或游标，不停已有撤回通道，保留唯一 worker。最新 CSV 覆盖与增量新车待处理分别核对。
- 只有一个同步进程持有运行锁。确认数据盘 60% 提示、70% 暂停重任务的规则和实际可用空间。自有备份核对当日定时执行、密文校验、已有恢复证据和可用的离机密钥。实际恢复用隔离数据库，清理只涉及本次恢复的临时材料。
- 运行 `observe-v2-sync.py` 保存连续 24 小时收件样本的成功数、待处理、错误数、最老待办及 P95。此读数止于应用时间。兼容的公开观测就绪后，单独从生效时间起记录供应商事件、本站收件、应用、详情与真实可见时间。撤回目标为收件到公开不可见 P95 ≤5 分钟，改价目标为收件到公开新报价 P95 ≤30 分钟。逐项记录整个样本、暂未公开、失败、跳过和观测缺失；报告到期仍待处理的数量和年龄。旧数据缺少公开时间时保持缺失。
- 新版 worker 接管后，通过管理员的 `GET /api/v1/admin/external/sync-timings` 核对 288 个五分钟接收时间槽。原定发布时间和成功处理时间分开记录。将库内公开投影时点和公网实访时点分别保存，抽验官网三语详情、目录及后台同一事件视图。失败、被替代和未全覆盖的样本留在原分母与状态中；只有连续覆盖满 24 小时后才能对该整段下结论。

## 车价汇率

- 切换前和 worker 交接后，都对正式库执行 `docker exec hd-auto-full-worker-1 node /app/production/worker-entrypoint.mjs fx-health`。先确认该容器是当前唯一正式同步 worker，实际库与 API 使用同一个生产库。核对健康退出码、正式来源和有效期。抽查原价为人民币的指定车源，确认接口的美元参考价及官网详情均恢复，保留原币金额和来源署名。已由负责人执行当次正式刷新时，后续只读核对。
- 若宿主已有经过验证的正式刷新任务，沿用同一个。否则在正式切换时将 `hd-auto-fx.service` 与 `hd-auto-fx.timer` 安装到 systemd，用 `systemd-analyze verify` 检查，执行 `systemctl daemon-reload` 和 `systemctl enable --now hd-auto-fx.timer`。确认定时器已启用、下次唤醒已排定，并在首次定时执行后核对服务结果及 `fx-health`。该任务每小时检查一次，同一生产库在滚动 24 小时内最多请求一次真实汇率。它使用现有非 root worker 的正式 FX 命令、凭据和数据库，在切槽和重启后沿用数据库中的限次记录。
- 回退前后核对当前 worker 容器名和库身份，继续由同一个定时器接管兼容版本。一次失败记录在服务日志和汇率状态中，有效旧报价继续保留；按健康状态追查，勿通过重置限次记录补跑。启用前若旧 worker 已有不同名称，先校对服务单元的目标，避免启动另一套同步或刷新任务。

## 大表迁移

- 以实际最终提交中的迁移 SQL 和生产迁移账本为准。先核对 `0039` 的事件、待办、索引行数和锁。依赖新增列的索引须在列存在后建立。未经候选迁移明确接管的同名索引不可提前放进去。按生产规模在隔离库记录事务、持锁和同步并行耗时后再放行。显式给本次 `migrate` 容器设置 `PGOPTIONS='-c lock_timeout=3s -c statement_timeout=30s'`，确认目标库会话采用该值。锁或 SQL 失败时保留旧版服务，在短窗口重试前再次核对账本和长事务。
- `0040` 对 `external_listings` 的外键和写入触发器、对 `external_listing_overrides` 的触发器需要短 DDL 锁。核对当前写入及长事务，选择短等待窗口重试；锁未取得时停止切换。
- `0044_external_power_price_facets.sql` 的大表索引先在事务外以 `CREATE INDEX CONCURRENTLY` 建立，同名索引须符合迁移中的精确定义。核对 `pg_get_indexdef` 的列、包含列、谓词和所属表，并检查 `indisvalid`、`indisready`、`indislive` 全为真。观察锁、任务积压、临时消耗、WAL 和系统余量。未验索引不交给 Drizzle。出现失败或存在同名未验证索引时，先排查并按批准的在线清理恢复。

## 平滑切换

1. 对准同版的库、服务、Redis、备份和回退材料。确认远端 `main` 与 `v2.0.0` 标签剥离后的提交一致，并记录已审构建树与镜像摘要。确认已验证的兼容迁移可由旧版继续使用。候选使用只读生产核对和独立本地联调，准备切回上一组完整的官网、Admin、API 和网关设置。保留已发布的新旧指纹资源以服务已打开的页面。
   首次从 v1 网关进入 v2 时，候选应包含最新的 `conf.d/00-edge.conf`、同槽 `default.conf` 与完整的 `hd-domains`。持有发布锁，使用 `prepare-v2-gateway.py` 指向实际候选目录并传入已核验的 `--expected-started-at`。脚本在网关重载锁内把四个新 include 保留为无功能占位，并补上缺少的默认关闭 Geo 文件。它验证旧配置的语法、运行容器和文件集，输出兼容回退包。然后按原有 `gateway-reload.py` 校验候选并平滑切换。回退使用兼容回退包，不临时删文件。IP 中继和 Geo 所需的只读挂载须在独立阶段核对，配置重载不会添加容器挂载。
2. 用发布锁串行执行。先完成兼容迁移和观测接入。如果小时导入已启用，暂停定时器并等待当前服务退出。平滑切换流量后，核对 API readiness、双域入口、会话和媒体、旧新缓存、唯一 worker 及备份定时。冷／热目录与切换后的首批请求分别记录。
3. 按已审候选的配置清单独立控制页面汇总、经同意的会话统计、Facebook Pixel 和公开索引。流量切换时各开关关闭，按当前授权与验收分别启用。`ANALYTICS_V2_ENABLED` 同时进入官网的构建环境、运行环境和 API 槽；启用官网时核对 `ANALYTICS_ORIGINS` 的精确来源。`PUBLIC_SEO_ENABLED` 独立传给 API 私网资格和详情读取。官网抓取由官网构建及运行的 `SITE_INDEXABLE` 控制，另核对 robots 和站点地图指针。正式供应商 worker 延续当前工作模式，沿用唯一进程和原游标。公司 Pixel ID 通过 `HD_META_PIXEL_ID` 配置，总开关 `HD_META_PIXEL_ENABLED` 默认关闭。网站构建和运行使用同一对配置。更换公司 Pixel 配置随网站与首页缓存同槽切换。按车选择由现有详情响应跟随车辆版本读取，保存后沿用现行缓存失效。验收使用合成 Pixel ID 并拦截外部事件。
   启用页面汇总前，先按[小时汇总手册](page-documents.md)核对稳定网关的覆盖心跳、小时定时单元及指定 API 槽的写入回执。匿名联系按 `ANALYTICS_ORIGINS` 配置的官网来源接收全地区点击。先启用新版 API，再加载清除地区头的新版网关。切换探针使用正确官网 Origin、`Content-Type: application/json` 和空对象 `{}`，预期收到带 `X-Request-Id` 的 JSON `400 INVALID_REQUEST` 和 `no-store`。另用不匹配的 Origin 验证 `403`。这两种探针均在写入统计前结束。回退地区限制版时，恢复该版配对的网关及 Geo 配置。[历史地区配置](analytics-geo.md)
4. SEO 先用同一份后端资格名单验证详情、互链、canonical、缓存和状态码。完整生成同代站点地图后再原子切换 index。每分片至多 10,000 URL、未压缩至多 50 MiB，仅对首批允许页面开放抓取。核对 robots 与 META 同步生效后再向有权限的站长平台提交。[Sitemap 协议](https://www.sitemaps.org/protocol.html)
5. 如需预热，只访问三语常用公开页与相应默认查询，按当前线上限流串行单次访问。出现 429、5xx、明显的延迟上扬或同步障碍即停止，保留预热的起止和实际命中证据。首批冷请求单列，隔离冷档未达标时保留该结论。

## 回退和开放后 48 小时

- 开关级回退关闭受影响的页面汇总、会话统计或 SEO，验证关键功能与缓存状态。SEO 回退将已开放的详情与 robots 恢复到受审版的索引策略，地图 index 回指有效的上一完整代或恢复空地图。旧静态资源在回退窗口内保留。
- 应用级回退沿用已验证的上一组部署配置及静态资源。回退前暂停小时导入，按实际接管的可写槽恢复导入配置。保留生产已写入的数据、兼容迁移、原 worker、同步游标和已有恢复点。发现新迁移与旧版不兼容时，先隔离确认恢复方案，再由用户决定数据变更。
- 开放首批索引时记录精确时间和地图代号。开放后取 0、1、6、24、48 小时检查点，核对可索引页面、分片 HTTP 响应、canonical 和跨语言互链、抓取或索引错误、数据库和应用负载、缓存命中、同步时延与 429。站长平台证据标注数据更新时间，缺权限标注待验。仅在 48 小时核对完成后决定是否扩大名单。
