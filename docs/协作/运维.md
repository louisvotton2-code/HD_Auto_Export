## 1. 目标部署与预算

默认单台海外 x86_64 Ubuntu 24.04 LTS，2 vCPU／4 GB 内存可起步，同预算优先 4 vCPU／8 GB；50–80 GB SSD 起（有 120 GB 更宽裕）。服务器、图片和备份总目标 150–300 元／月；实际选择以账号可购买套餐、续费价和网络验证为准。

```text
公网 HTTPS
  → 反向代理（Nginx 或经验证的等效方案，OPS 统一选定）
    → 官网 apps/web：Next Node／standalone
    → 后台 apps/admin：React/Vite 静态产物
    → 业务 API apps/api：独立 Node 服务
      → PostgreSQL（私有容器网络与持久卷）
      → 本地私有磁盘（展示WebP，公开访问由API鉴权）
      → 后续第三方车源／外部 AI

数据库一致性备份 + 图片清单/必要副本
  → 异地、独立凭据的备份存储
```

这是已采纳的目标部署分工；三个应用已在新服务器运行，生产只读核验结果见[正式上线记录](../日志/2026-11-09/运维-OPS-02-正式上线与交接.md)，运行材料见 [deploy/runtime](../../deploy/runtime/README.md)。单仓的应用各自产出成品、可独立发布；统一锁文件不要求同时发布全部应用。部署同机是初期预算方案，升级服务器不能代替灾难恢复。容器将进程与依赖分开，但不会消除主机故障；后续有实际容量／恢复要求再拆数据库或增加实例。

## OPS-01：本地可验证的运行材料

当前应用及Compose组合已在本机验证；以下保留运行材料和后续迁移检查要求，实际证据见本轮日志：

- 分别与 FE／AD／BE 明确启动和构建命令、产物路径、端口、健康检查与环境变量；API／Node／PostgreSQL 版本按负责人核验锁定，不能只用 `latest`。官网产物为完整 `apps/web/.next/standalone/`；后台 `apps/admin/dist/` 与API `apps/api/dist/` 及依赖／migrations分别打包。
- 在 `deploy/runtime/` 按应用准备 Dockerfile／静态托管配置、Compose、反代与无密钥示例，不覆盖现有静态部署材料。按域名或路径将 web、admin、API 分别路由，明确后台 SPA 回退、API 前缀、登录回调、Cookie／CSRF／CORS 及官网 SSR 的内部 API 地址；公开客户端不能看到内部凭据。
- 生产镜像在匹配目标的 Linux/amd64 环境构建；Mac/arm64 开发机不能直接上传其原生 Node 依赖。构建放开发机的对应容器或 CI，低配生产主机主要跑服务。
- 数据库目录和上传数据在镜像外；应用和数据库使用独立最小权限身份。DB 端口不映射公网，管理接口鉴权且 no-store。
- 区分开发、预发布和生产的账号／库／桶／密钥。预算有限时预发布可本地／临时实例完成；不要在生产库跑测试，也不声称同机两容器具备隔离灾备。
- 给日志设置轮转与容量限制，健康检查／重启策略不形成无限重启风暴；第三方故障不让整个精选应用重启。

验收：已建立的三个应用各自构建产物与源码版本可追溯，空环境可按文档启动目标组合；服务间访问正常；重启后记录和图片引用保留；密钥不在前端产物／镜像层／仓库中；可以恢复一份测试备份。

## OPS-03：监控和扩容（G3 及以后）

- 监测 HTTP 可用性、5xx、响应时间、CPU／内存／磁盘、数据库连接与慢查询、备份新鲜度、证书有效期、图片错误、供应商额度和失败。
- 初始告警建议：持续内存 >80%、磁盘 >75%、CPU >70% 且影响响应、备份超 26 小时未成功；这些是调优起点，不是通用容量保证。明确接收人和渠道后再开通知，不擅自向他人发送消息。
- 对俄罗斯、白俄罗斯、中亚代表城市及中国运营人员分别测试 HTTPS 首页、图片和管理上传，覆盖不同时段／网络；仅凭德国地理位置不能保证所有网络可达。
- 高资源占用先确认慢查询／缓存／图片流量，再考虑升 4C8G、拆数据库或托管库。实际故障域／恢复要求决定是否多机；不为“后续会有 AI”提前买 GPU。
- CDN 根据实际访问测试和图片成本再选，域名注册不自带已配置 CDN；启用 CDN 时 admin/API/私有图片及失效策略需单独配置。首期不自动套全球代理，避免未经测试影响目标市场访问。
