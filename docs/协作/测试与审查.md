# 测试、代码审查与阶段验收

2026-11-13｜工作流 QA／Review｜当前为开发验证期，尚未正式运营。以下为现行规则；文末历史结果只属于当时版本。

先按 [接手导航](../README.md) 阅读 AGENTS、当前进度、自己的角色及相关契约。用户或本轮负责人须指定要审查的任务、基线与范围；不因路线图存在就主动实施所有阶段。测试／审查角色可由独立 Agent 或人员承担，同一作者的自评不能替代独立 review。

## 当前阶段与节奏

**开发期默认：受影响端自测 → 一次独立审查 → 必要的跨端联调 → 精简交付。** 不要求每次修改跑全站回归、全量性能测试或重新建立完整证据包。

- 阶段唯一配置为 [.github/verification-policy.json](../../.github/verification-policy.json)，当前 `development`。正式运营前单独安排功能、性能、安全、备份恢复全量验收；完成后同一发布将阶段改为 `production`，恢复每个代码 PR 的全仓自动检查。不能用环境变量临时降级。
- 服务器已可访问不等于已正式运营；开发期也不能放松真实数据、账号权限、密钥、金额、收费调用与生产备份的保护。
- 实现者日常只跑与修改有关的测试。准备推送时以 `verify:push` 的受影响范围检查收口，不先手动重复运行整套 `check/build/test:e2e` 再跑一次门禁。
- 同一 diff 由一位独立 Reviewer 审查即可，修复交原 Reviewer 看增量。PM 核对交付条件，不再重复代码审查或第三次执行相同测试。没有独立审查能力时标待审查，不由作者填写“独立通过”。
- 跨端边界改变才联调，由指定一人执行一次并共享结果；单端改动直接按受影响行为验收。旧失败保留一行原因及定向复测结果，不为每次复测另建全套记录。
- 可维护性保留：接口与职责边界、清晰命名、必要类型／约束、关键失败路径测试、无用代码清理。小问题不扩成无关重构；未来优化记待办，不自动升级成当前交付的前置任务。

## 谁负责什么

| 责任方 | 输入与交付 |
| --- | --- |
| 实现者（FE／BE／AD／OPS） | 完成分配范围；自测受影响行为；交付源码版本、diff、环境、运行方法、实际命令与结果及未覆盖项 |
| 独立 Reviewer | 只读审查指定 diff、相关实现和测试；核对功能、依赖边界、失败路径、数据公开与权限；报告可定位的问题，不顺手改作者代码 |
| QA | 使用各端共同契约和成品跑集成场景，记录实际结果、复现路径与缺陷；修复后确认受影响问题和必要回归 |
| PM | 核对证据是否属于同一版本／环境、是否覆盖本阶段门槛、是否有未处理阻塞；汇总实际状态与业务验收清单 |
| 用户 | 验收业务事实、流程、视觉和真实内容；测试数据通过不能替代真实车源／图片确认 |
| OPS | 有目标环境和发布授权后部署，登记各应用产物与兼容版本，做上线冒烟；按故障情况回滚并记录结果 |

Reviewer 可以运行有必要的只读检查和隔离测试；不接触生产数据，不改待审代码。问题交回原负责人修复后再审，独立审查者不因帮忙修复而省略复查。QA 的集成测试不替代实现者自测，也不替代用户的视觉和业务判断。

## 状态和交接顺序

`待开始 → 进行中 → 待审查 → 待联调 → 待验收 → 已验收`。无跨端依赖的任务可在 review 后直接进入待验收；历史“待用户验收”统一理解为待验收。受阻时写清依赖和负责人，可做部分继续推进。

1. 实现者自测并交齐版本与结果后标待审查；独立审查发现阻塞退回进行中。
2. 审查通过，有跨端依赖则标待联调。QA 针对指定成品、API／契约及数据库版本验证，不用旧构建或混合版本证明新代码通过。
3. 所需 review、集成与复测证据齐备，PM 核对阶段门槛和未覆盖项后标待验收，交用户业务／视觉确认。
4. 用户确认后标已验收；发布状态另记。代码已验收、已提交、已推送、已部署是四个不同事实。

P0（如重大数据破坏、广泛敏感信息泄漏）和 P1（如鉴权绕过、发布闭环不可用、严重错误公开事实）阻塞验收与发布，修复及复测后才能继续。P2 为非阻塞缺陷／改进，须有明确负责人、处理计划和 PM／用户接受依据；不能用“以后再说”隐藏。分级结合发生条件与影响，报告提供证据，不只贴严重度标签。

## 测试范围按改动选择

| 改动 | 开发期必要验证 |
| --- | --- |
| 仅 Markdown／Skill | 链接、围栏、空白及规则一致性；不启动应用 |
| 单端代码 | 对应应用类型／单元／构建，公共依赖构建及 workspace 边界；不顺带重测其他两端 |
| 页面文案、样式、交互 | 上述自动检查之外，人工或定向浏览器看受影响页面／行为；布局看代表性桌面与手机宽度，语言只覆盖改动及可能溢出的内容，不默认全页三语截图 |
| API／身份／数据库／发布 | API 检查及隔离数据库集成；重点覆盖修改涉及的权限、事务、人工覆盖、撤车／缓存失效、金额／日期空值、翻译预算；不删除这些保护测试 |
| 公共 contracts | schema 测试与全部受影响消费者检查／构建；实际交互变化时联调一个代表闭环 |
| 税费、美元计算 | 变动公式的边界、舍入、缺失／非法与说明一致；不因计算变动重跑无关页面 |
| 锁文件、根配置、CI、部署、未识别目录 | 保守执行全仓自动检查；另按实际风险检查代理、备份、迁移、回退。已完成且未改变的恢复演练不因文案变动重做 |

本地 `verify:push` 和 PR CI 共用 [范围选择器](../../scripts/verification-plan.mjs)：开发期单端修改只执行对应 `check/build`，API 仍包含 `test:integration/openapi`，contracts 修改覆盖三端。普通开发期不自动执行全量浏览器套件，所需定向交互检查在任务日志写实际结果，由 Reviewer 核对。自动选择是最低门槛；影响跨端行为时不能用“编译通过”替代联调。

仅 Markdown 始终用文档检查。阶段缺失／无效、未知路径、基础设施或规则变化退回全量，不能静默漏测。正式运营期代码改动及手动全量检查执行 `pnpm check → pnpm build → pnpm test:e2e`。正式运营前的压力、安全和备份恢复验收另列实际场景，这三个命令不代表全部业务验收完成。

检查名称以各应用 `package.json` 为准。定向官网场景可用 `pnpm --filter @hd/web exec playwright test tests/<相关文件>.spec.ts`，后台真实联调按其 README。后端集成使用隔离测试库；不使用生产数据库。定向检查通过后，只有代码变化、失败或明确的新风险才扩大／重跑，不为测试数量增加工作。

Next 的 dev／typegen／build 不能并发写同一 `.next/`；同一任务尽量复用已验证的同版本成品，不让多个 Agent 重复安装、构建、开相同服务。确需隔离的端口、数据库和输出由负责人分配，结束后清理本任务资源。单元／构建通过不能推定视觉、权限或真实服务器已验收。

## 推送前检查

这是所有角色的常规交付要求，Agent 应主动执行，用户无需每轮重复。实现者与独立 Reviewer 分工：实现者完成修改和自测；Reviewer 只读检查真实 diff、验证范围与失败路径；问题交原作者修复并复查。保存本地提交后，Reviewer 核对提交内容与已审差异一致，再把结论绑定完整 SHA。独立 Agent 可作为子 Agent 执行；工具不支持时交 QA／PM 协调，不能把作者自评改名为独立审查。

### 开工时启用

```sh
pnpm hooks:install
pnpm hooks:check
```

`hooks:install` 在 Git 公共目录安装持久 pre-push 入口，并设置仓库本地 hooksPath；不会覆盖其他自定义 hooks。`hooks:check` 核验当前工作区实际入口。linked worktree 共用 Git 配置，入口会定位本工作区的检查脚本；切到没有脚本的旧分支会拒绝推送，须先协调共同基线。新 clone 需要重新安装；依赖安装的 prepare 仅提供便利，重复安装、CI 或禁用生命周期时可能不执行，不能据此省略显式检查。

Codex 在启动时读取根到工作目录的 AGENTS；正在运行的旧会话未必自动刷新，规则调整后重新读取一次。其他工具若不识别 AGENTS，应一次性配置同一公共入口。新 Agent 应从包含当前规则的共同工作分支开始，不从旧 main 的工程结构自行重建。[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

### 测试与审查记录

完成实际自测、独立 review、修复复查并保存提交后，在根目录执行：

```sh
pnpm verify:push --base <本轮基线完整SHA>
pnpm review:record --base <同一基线完整SHA> --sha <待推送完整SHA> --reviewer <独立Agent标识> --report <报告JSON路径>
pnpm hooks:check
git push origin <工作分支>
```

基线应覆盖全部待推送变化：已有远端分支通常以其当前头提交为基线；新分支以该命名远端已公开、可由本地 tracking refs 确认的共同基线为起点；先 fetch 对应远端，hook 自身不联网补历史；新分支只在单一 fetch／push 地址与 Git 实际推送地址一致时采用该远端的 tracking 基线，分离地址或多推送地址先协调。推送前先 fetch／核对远端，不能选更晚的基线而漏审之前的改动。最终提交发生 amend、rebase 或新增提交，门禁仍要求匹配新 SHA。Reviewer 可复用已审结论，只核对新差异并重新绑定，不重新读一遍全部代码；不要为了补一行重复日志反复制造新提交。

`verify:push` 要求当前已提交源码与索引干净，非忽略的未跟踪文件也须处理（本机 `.vscode/` 例外）；验证记录写 Git 私有目录，不提交。只有实际检查全部成功才生成测试记录，开始重跑会使旧成功失效。同一仓库使用验证锁串行生成记录；若中断留下锁，须先核对 owner.json 的进程与工作区，确认没有验证运行后才清理并重跑，不能删除活动锁来绕过检查。检查由前述阶段及改动范围自动选择；全量场景才运行根 `check → build → test:e2e`。清除外部 E2E 地址，不借旧服务冒充新版本。纯 Markdown 检查空白、引用与围栏。增加应用时同步范围选择器；未识别目录先走全量。不要关闭 hook、篡改收据来追求提速。

Reviewer 产出以下 JSON 报告。summary 写审查范围、发现及处置、测试证据与未覆盖项；存在未处置 P0/P1 时不能填 pass，P2 按前述接受规则写清。示例中的占位符不能原样登记：

```json
{
  "base": "基线的完整提交SHA",
  "sha": "待推送的完整提交SHA",
  "reviewer": "独立Reviewer标识",
  "verdict": "pass",
  "unresolvedP0": 0,
  "unresolvedP1": 0,
  "summary": "真实审查范围、问题处置、验证证据和未覆盖项"
}
```

`review:record` 只登记已完成的审查，不会调用 AI 或替作者进行 review。报告放在 Git 私有目录或本机证据位置；记录保存原报告路径和内容哈希，修改／丢失报告会使记录失效。记录是可追溯的本地流程证据，不是审查人身份认证，也不授权作者编造独立报告或手工测试通过记录。

pre-push 检查 Git 实际准备推送的每个 ref 和完整 SHA，包括非 HEAD 提交；验证非 HEAD 提交时先在对应分支或隔离 worktree 中将它作为 HEAD 运行 verify:push，再登记该 SHA 的报告，不能拿当前 HEAD 的测试顶替。缺少匹配证据、漏审范围、一个 ref 不合格都会拒绝整次推送。默认拒绝直接更新 main、删除、tag／其他特殊 ref、非 commit 对象、非快进或未知旧远端对象。失败先处理原因，不自行使用 `--no-verify`、关闭 hooks、伪造记录或降低远端保护。通过门槛仍须遵循本轮外部推送授权。

### 远端 main 的保护

CI 保留必需的 `verify` 作业，但只在 **PR 更新** 和手动 `workflow_dispatch` 执行，取消分支 push 与合并 main 后的重复运行。PR 按范围检查，手动运行始终全量；不加路径跳过规则导致必需检查永久等待。不更改远端 main 保护，也不取消其他任务正在执行的 CI。合并后核对 main 与受检 PR 的代码内容；若合并方式产生未受检的代码树，须补做验证。发布记录写实际 PR 检查和 main SHA，不声称 main 有一次未执行的 push CI。


本仓库 main 要求 PR、与 main 同步后的 `verify` 检查（来源限定 GitHub Actions）、解决审查对话；管理员同样受约束，禁止强推和删除。所需参数保存在 [.github/main-protection.json](../../.github/main-protection.json)，变更文件不会自动更改远端，配置后必须读回核对。用户明确选择不增加 GitHub 审核账号，故 GitHub 必需批准数为 0；专门 Agent 的独立 review 在本地完成，不能把多个 Agent 当作多个 GitHub 账号。

远端保护限制 main 更新，不会证明所有功能分支在首次上传前已被 Agent 审查；本地 hook 也可被有本机控制权的人绕过。规则依靠统一入口、实际检查和独立报告减少漏做，不能宣称不可绕过或自动发现全部缺陷。没有另行引入 AI 服务、账号、密钥或收费 review 产品。

## G1 集成基线

以同一稳定车辆 ID 验证：登录 → 创建草稿 → 上传完成与失败 → 草稿不可公开 → 校验发布 → 三语首页／无需重建的新详情 → 正确联系草稿 → 库存变更／下架 → 首页及详情状态同步。再覆盖未登录／越权、公开字段泄漏、409 不覆盖、保存不隐式发布、待询价不变成 0 和缺失日期不补造。

隔离测试样例须保留测试身份；当前公开样例下架、文案与激活行为遵循[用户最新产品约定](../../product/路线图.md#当前公开展示与交互)，不再强制旧来源／库存待核验展示标签。内部事实、来源／图片许可与审核状态不能因文案调整变成已核验；真实车辆与图片由用户核对。联系链接可检查账号、编码、车号和详情 URL，不向真实客户发送消息；收件链路实发由用户测试账号执行或按明确委托实施。后续 G2／G3 按路线图加运营恢复与供应商故障场景，不提前把未实现功能写成失败或通过。

## 审查与缺陷报告最小内容

每个任务复用 [同一份任务记录](../README.md#每轮如何记录)，只需：版本与范围、实际检查结果、阻塞／未覆盖项、下一步。问题写位置、触发方式和影响，修复后追加结果；长输出、逐文件哈希清单、每次截图和多份复测报告不作默认要求。确有追查价值的失败、数据核对与恢复材料保留在私有位置，日志只链接。

独立审查仅保留上面的机器可读 JSON 报告和任务记录中的一句摘要，不再要求另一篇内容相同的审查文章。授权、最终 SHA、关键失败和未完成项不能省略；发布、迁移、数据清理仍需保留可用回退材料。与任务无关的 P2 改进记待办，不让审查扩大当前实施范围。

PM 只核对真实结果，不每隔几分钟催问或重复拉取所有日志。文件约定不会自动跨对话同步；规则更新后，正在运行的对话在下一交接点重新读取一次。
