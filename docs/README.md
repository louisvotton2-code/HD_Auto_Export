# 接手导航与协作流程

这是本仓库唯一的接手入口和日常流程正文。先读[当前进度](开发进度.md)，再按本轮任务选择角色和技术资料。用户当前任务决定范围；旧日志与路线图不授权额外实施、外部服务或生产操作。

## 开工与固定工作区

**单端任务可以直接在原角色聊天派发，不必先经过 PM。** 接单角色确认任务 ID、范围、基线及验收条件；涉及跨端接口、共享文件、集成或发布时，由 PM 协调负责人和依赖。各端复用原角色会话与下列固定目录，每个角色只有一个长期工作树：

| 角色 | 固定目录（相对主目录） | 分支约定 |
| --- | --- | --- |
| PM 集成 | `.` 主目录 | 集成期间用任务分支；合并收尾后回到 `main` |
| FE | `../websit-worktrees/fe` | `codex/fe-<task>` |
| AD | `../websit-worktrees/ad` | `codex/ad-<task>` |
| BE | `../websit-worktrees/be` | `codex/be-<task>` |
| OPS | `../websit-worktrees/ops` | `codex/ops-<task>` |

1. 核对实际目录、分支、已有改动与权限；本仓库独立于父目录其他项目。规则变更后，原角色会话重新读取本入口和本轮任务，确认对固定目录有写权限。
2. 获取最新 `origin/main`，并**实际更新基线**：上一任务已合并且工作树干净时，将本地基线快进到 `origin/main`，再在同一目录创建下一条角色任务分支；仍有本轮独有提交时由负责人合入新主线并处理冲突。记录实际基线 SHA，不能只 fetch 就声称已同步。若当前规则尚未合入主线，使用 PM 指定且包含本轮规则的共同基线。
3. dirty 工作树、独有提交、运行进程与私有资料先保护并交接，不覆盖、不强制重置、不从旧 HEAD 另开一套重复目录。目录尚未迁移完成时由 PM 记录实际落点，不将本表当成已迁移证明。
4. 每轮运行 `pnpm hooks:check`；新 clone 或未启用时执行 `pnpm hooks:install` 后复查。旧分支缺脚本先协调共同基线；安装失败不能记为已启用。检查与命令细节见[测试与审查](协作/测试与审查.md#开工时启用)。

接单开工时，只在**自己的角色进度摘要**登记一次任务、状态、目录／分支／基线、修改范围和共享依赖；后续仅在阻塞、协助、交付时更新。同一固定工作区由一个原角色聊天统筹写入，不另开第二个聊天同时修改它。发现既有未完成工作先保护并判断是否可衔接，不把新任务直接覆盖到旧改动上。

PM 在新一轮分派或集成前，一次读取四个**实际固定工作树**中的角色摘要，并核对 Git 改动和原会话状态；不能仅凭主目录中尚未同步的摘要推定其他端空闲。总览 `docs/开发进度.md` 由 PM 统一汇总，各端不争写；不另建状态平台、不持续轮询催报。有跨端变化时，相关端交齐后由一人集中完成一次必要联调，修复只复核增量和受影响场景。

**PM 默认不驻留等待其他角色。** 分派、协调或本角色工作完成后，没有可独立推进的待办就结束当前回合，简述已完成与待谁处理；不得通过反复 sleep、读取对话／进度／Git／CI 状态来保持等待，也不创建监控自动任务。各端继续独立执行，只在阻塞或需要跨端协助时主动联系 PM，说明问题及需要的决定。没有协助请求时，由用户看到各端完成后通知 PM；PM 届时一次读取交付证据，集中验收与汇总。角色完成结果仍留在各自对话和既有角色记录，不要求逐步汇报或逐个唤醒 PM。只有用户明确要求 PM 持续跟进某次执行时才例外；一般的分派、验收或发布授权不自动视为持续等待授权。执行者对自己启动的必要检查和发布操作仍负责确认结果，不能把“PM 结束回合”当成任务已经完成。

## 本地开发与部署分工

- **用户验收只使用 `http://127.0.0.1:3363`**，同源提供官网、`/admin/` 和对应 API。3317／3318／3320 仅为内部开发端口，不作为另一个用户验收地址；是否已接入同版服务由实际核验和进度记录确认。
- FE／AD／BE 自行运行 `pnpm dev:web`、`pnpm dev:admin`、`pnpm dev:api` 并热更新；OPS 负责共享依赖、3363 代理和发布设施。共用指定开发样本库、缓存、媒体与配置，测试使用隔离库和输出；依赖监听回环地址或受控私网，保留鉴权、Cookie、Origin／CSRF、预览和媒体保护，不使用生产库或默认触发收费、同步任务。
- 仅接手或依赖变化时安装；公共契约变化后构建并通知消费者。Next dev／typegen／build 使用独立输出或串行运行。官网 Node 成品、后台静态产物和 API 分别核验，不使用历史 `out/` 代替当前产物。
- 实现者自测受影响范围，一位独立 Reviewer 只读审查；跨端变化由一人复用环境完成必要联调。修复后复核增量和受影响场景。单端检查不代表跨端通过，具体范围及 P0／P1 门槛见[测试与审查](协作/测试与审查.md)。PM 集中核对版本与证据，仅在阻塞、需要决策或交付时汇报。
- PM 提供 3363 的实际版本、关键结果与限制，用户验收业务、视觉和真实内容。状态按 `进行中 → 待审查 → 待联调（如需）→ 待验收 → 已验收` 记录；受阻注明负责人和可继续工作。临时测试资源用完释放，旧预览先确认替代可用再关闭，保留数据和回退材料。

## 提交与发布

1. 用户验收最终修改并授权提交后，冻结候选、核对暂存范围并保存提交。凭据、真实环境文件、数据库、备份和 `docs/private/` 不提交；贡献检查见[贡献者说明](../.github/CONTRIBUTING.md)。
2. 对准确的基线及待推送 SHA 执行[推送前检查](协作/测试与审查.md#推送前检查)：实际自测、独立 Reviewer 报告和 `pnpm verify:push --base <基线SHA>` 必须匹配该提交。后续修改或新提交需核对增量并重新绑定，不能沿用旧收据；禁止绕过 hooks、伪造记录或降低远端保护。
3. 按当前明确授权推工作分支，经 PR、GitHub Actions 必需的 `verify` 和分支保护合入 `main`；禁止直接推送、强推或删除 `main`。核对合并树与受检候选，树有变化则补验证。独立 Agent 审查在本地完成，不冒称 GitHub 已认证其身份；检查通过不自动授予推送、合并或部署权限。
4. **只有需要应用发布时**，在最终 `main` SHA 通过 GitHub 创建 `vX.Y.Z` 标签，核对远端指向；已发布标签不能移动或覆盖，常规修正递增补丁版本。仅文档整理无需应用版本。OPS 按[运行手册](../deploy/runtime/README.md)部署该标签对应产物，核对兼容迁移、双域、API／worker、备份与回退点，记录实际结果；Git 推送不等于部署。
5. 合并收尾后 PM 主目录回 `main` 并快进到最新 `origin/main`；各角色在原固定目录更新主线基线，准备下一任务分支。保护未提交内容和独有工作，只回收本任务临时资源。

## 记录与交接

每个任务只用 `docs/日志/YYYY-MM-DD/角色-任务ID-主题.md` 一份记录：范围和版本、结果、实际验证与未覆盖项、交接或下一步。关键失败与修复复测追加原记录；机器收据和独立审查 JSON 留在私有位置，公共日志不写凭据或业务隐私。

角色在阻塞、交付或交接时更新自己的摘要与日志链接，PM 汇总[当前进度](开发进度.md)。代码完成、用户验收、提交、合并和上线分别记录实际状态。业务规则或维护方法变化才更新对应技术文档，不复制流程正文。

## 文件放在哪里

- 根 `README.md`：项目简介、源码目录和本地命令；`AGENTS.md`、`CLAUDE.md` 与公共 Skill 只路由到本入口。
- `docs/协作/`：角色任务、进度摘要与测试门禁；`docs/开发/`：架构、契约和模块维护。
- `product/`：产品决定和路线图；`docs/日志/`：实际交付；`docs/research/`：专题研究；`docs/归档/`：被替代的历史材料。
- `docs/previews/`：已有视觉基线；`docs/private/`：本机私有资料，忽略且不提交。

公共规则和 Skill 随 Git 统一维护，各工作树读取自己已同步基线的副本，不分别改写或链接到其他分支的未提交规则。公共接手 Skill 仅保留 `hd-auto-development`。

`docs/private/` 只保存本地运行配置与数据、必要私有证据、待核对的恢复归档；Git 忽略不等于加密或备份。不得在其中新建完整工作树、公共流程或当前任务的唯一说明。旧目录仅在独有改动和私有内容已保护、无运行或会话依赖后回收；保留项和实际位置记在当前进度，本机恢复清单留私有目录，不复制多套样本库。
