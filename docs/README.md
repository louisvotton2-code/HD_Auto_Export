# 接手导航

这是本仓库唯一的文档导航。**先确认现状，再选自己的职责；不用把全部文档读一遍。** 当前用户任务确定本轮范围，路线图不自动授权后续阶段。

## 新 Agent 从这里开始

1. 按 **根目录 [AGENTS.md](../AGENTS.md) → 本导航 → [当前进度](开发进度.md) → 自己的角色文件 → 本次相关契约** 阅读，确认实际能力、环境和阶段。用户须指定角色和本轮任务；目录或路线图存在不代表允许自主实现全部模块。
2. 加载 [hd-auto-development](../.agents/skills/hd-auto-development/SKILL.md)。支持 Skill 的工具可显式使用 `$hd-auto-development`；其他 Agent 直接读取同一文件即可，无需安装第二套规范。
3. 按下表只读自己的角色文件及任务所需资料，检查实际代码和已有改动，然后执行。身兼多职时按本轮涉及的职责补读，跨角色变更先协调文件归属。
4. 交付时更新本角色进度和本轮日志。总进度由产品／项目管理汇总，历史日志不反复复制。
5. 每轮确认 `pnpm hooks:check` 通过；新 clone 先 `pnpm hooks:install`。功能自测后主动安排独立 Agent review，按 [推送前检查](协作/测试与审查.md#推送前检查) 登记对应提交的实际证据。无需用户每轮重复提醒；正在运行的旧对话需先重新读取更新后的 AGENTS 和本导航。

## 文件放在哪里

```text
AGENTS.md                      Agent 自动读取的短入口与底线
README.md                      项目简介、本地运行和源码目录
.github/CONTRIBUTING.md         验证、Git 与交付约定
.agents/skills/hd-auto-development/  工作流程及按需规范
apps/web/                      已迁移的官网 Next.js 应用（当前静态导出）
apps/admin/                    员工后台预留，React/Vite 工程待 AD-00 建立
apps/api/                      独立 API 本地实现，运行方式见包内 README
packages/contracts/            公共 DTO/schema、推导类型与隔离样例
packages/calculator-core/      共享计算预留，出现真实第二消费者后再提取
product/                       当前路线图、业务决策和选型证据
docs/
  README.md                    本导航：去哪读、谁负责、怎么记录
  开发进度.md                  当前实际状态与阶段摘要，PM 维护
  开发/                        当前架构、模块维护、接口及模块说明
  协作/                        每个角色一份职责＋任务＋进度摘要
  日志/YYYY-MM-DD/             每轮实际交付和验证证据
  research/                    专题研究、规则覆盖和测试参考数据
  归档/                        已替代规划与历史部署、进度快照
  previews/                    已有视觉基线与截图材料
  private/                     本机私有运维资料，忽略且不提交
```

根目录仅保留 `README.md`（项目说明）与 `AGENTS.md`（Agent 入口）两份 Markdown。开发／验证／Git 细则读 [贡献规范](../.github/CONTRIBUTING.md)；应用构建配置归各自应用；pnpm workspace、统一锁文件与集成脚本位于根目录，不当作散落文档搬走。旧交接 ZIP 已原样移入 `docs/private/archives/`，仅本地保存，不作为开工资料或提交内容。

已采纳单仓多应用。官网仍静态导出；API 与 contracts 已建立本地实现，最新验证和联调状态见[后端摘要](协作/后端.md)。admin 与 calculator-core 仍预留，当前计算核心归官网。具体位置和共享条件在[仓库与目录边界](开发/模块维护.md#仓库与目录边界)维护。

**一个事实只设一个维护入口：** 当前状态在进度，业务决定在路线图，接口在车辆接口，操作步骤在角色任务，执行证据在日志。其他地方用链接，不重复写长篇。技术文档须区分“已实现”和“方案草案”；遇到与代码冲突先核对并记录，不能靠改文档把未实现能力写成完成。

新增文档先判断能否更新已有文件；新增时放入对应目录并从本导航或相关角色／模块文档链接。迁移同回合修复入站链接和 Skill 引用，不在根目录留多份“最新计划”。过时材料放归档并标注被哪个当前文档替代。

| 独立 review、集成场景与缺陷报告 | QA／Review；审查者不能以作者自评替代 |

分工前核对包含本轮工程迁移及既有官网功能的共同 Git 基线，记录见 [PM-ARCH-02](日志/2026-11-08/产品项目-PM-ARCH-02-工作区迁移与验收流程.md)。不能从旧 `06b1c4a` 建工作目录后把缺失功能当不存在。尚无已提交共享基线时相关文件串行操作；从已保存基线并行时使用独立 worktree、`codex/` 分支、端口、数据库、构建和测试输出。不得清理或覆盖他人改动。

## 每轮如何记录

任务状态统一为：`待开始` → `进行中` → `待审查` → `待联调`（有跨端依赖时）→ `待验收` → `已验收`；`受阻` 须注明阻塞、负责人和可继续部分。历史 `待用户验收` 对应 `待验收`。

- 实现者自测并提供版本／diff／检查证据后进入待审查；独立 review 通过后进入联调，单端任务可直接待验收。审查或联调发现阻塞问题退回进行中，修复后按受影响范围复查。
- QA 验证集成场景，PM 核对证据与阶段门槛，用户完成业务／视觉验收。P0/P1 阻塞进入待验收；P2 须有负责人、处理计划和明确接受依据。完整职责和报告要求见 [测试与审查](协作/测试与审查.md)。
- 标清本地、CI、预发布或生产。验收通过不等于已部署；发布由 OPS 在已有授权及实际环境下执行，并记录冒烟和回滚结果。

1. 在自己的 `docs/协作/角色.md` 进度表更新任务状态、日期、日志链接和下一依赖；同一任务复用原行。
2. 新建 `docs/日志/YYYY-MM-DD/角色-任务ID-主题.md`，例如 `后端-BE-01-运行时基础.md`。同任务同日多轮可加 `-02`，不覆盖既有证据。无既有任务编号的维护先在本角色表登记。
3. PM 依据这些证据更新总进度；角色无需同时改总进度。摘要过期时查看其日期和最新日志，PM 未复核记“待核验”，不假设跨对话已自动同步。

日志使用以下最小模板，按需要增加内容，不堆贴完整终端输出：

```markdown
# 角色 / 任务ID / 主题
日期：YYYY-MM-DD（Asia/Shanghai）
状态：进行中／待审查／待联调／待验收／已验收／受阻

## 范围与版本
- 用户目标、本轮范围；分支、基线 commit、待交付 commit 或未提交 diff 标识及所涉应用／包。
- 实际环境、运行方式和测试地址（不写凭据）。

## 实际变更
- 已完成能力、主要文件入口；相关契约／决策变化及原因。

## 验证与限制
- 实际执行的检查、对象与结果；失败和重跑分别记录。
- 未执行项、未覆盖项、依赖或阻塞；不复制历史通过数量。
- 独立审查者与报告、集成测试／缺陷复测、PM 核验证据、用户验收结论；未发生则写未执行。

## 交接
- Git 提交／推送状态；部署状态，分别记录。
- 下一步、接手角色及依赖；链接相关任务或维护说明。
```

历史记录从 [归档索引](归档/README.md) 查。公开日志不写密钥、会话、客户隐私或原始生产数据。

可直接给新对话的开工语：**“先读仓库 AGENTS.md，通过接手导航找到你的职责。你负责【前端／后端／后台／运维／产品项目／测试与审查】，本轮执行【任务或问题】；按统一规范交付并记录角色进度和日志。”**
