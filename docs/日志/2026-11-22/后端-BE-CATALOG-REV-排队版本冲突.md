# BE-CATALOG-REV 目录排队版本冲突

基线为生产 v2.0.0 的 `2df822c1000db3181cad00014294c8b02388f994`。本轮范围为后端目录列表、详情和首页车源的公开路由与受保护 SSR 别名。

## 诊断与修复

正式 20 并发首波有 5 次 API 503，其中列表 2 次、详情 2 次、首页车源 1 次。服务端记录 `PUBLIC_CATALOG_CHANGED` 和版本重试耗尽。采样时主机 CPU 约 48%，未见数据库锁等待。另有 4 次 429，由现有限流独立产生。

缓存查询在进入回源队列前读取目录版本，业务事务稍后才建立读取快照。同步在两者之间提交时，旧版用前一个版本标记实际已读到的新数据，浪费一次回源并可能耗尽重试。本轮在同一个只读事务中读取目录版本及车辆数据，读后核对当前版本。排队期间已更新且仍为当前版本的数据按实际版本缓存。如果业务读取期间又提交撤回、恢复纪元改变或当前报价切换，仍执行有限重试并保护失效。回源并发、队列、重试次数、公开格式和筛选缓存策略沿用现有实现。

## 验证与交接

- API 类型检查、303 项单测、构建、OpenAPI、工作区边界和 hooks 检查通过。
- 隔离 PostgreSQL 定向集成 29 项通过，包含列表、详情和首页车源的公开及 SSR 路由在排队期间升版后一次回源、正确版本及随后缓存命中。真实提交撤回后，同一详情请求返回 404，下一次列表与首页均不再返回该车。覆盖既有 USD／游标、Pixel、SEO 的版本和失效行为。
- 历史日志无法逐条区分排队窗口与业务事务期间的真实变更。待 OPS 在同步运行时复测公网同档并发，对比各路由 503、429、回源次数与 P95，并复核撤回。正式负载表现和真实网络链路待 OPS 核验。
