归因基线为生产 v2.0.2 `af62315ae174ae4d40aa713301e3a7a25a72f3b3`，修复独立叠加在 v2.0.3 的后端候选 `6ce2860854115e5c40c8f67efe700d724f8e14a5`。同一个 worker 重复出现 `e45ef7ddb0e2`，与生产源码两处 `UPDATE external_full_events SET public_effective_at` 的完整 SQL 指纹相符。该语句跟随每车详情落库和撤回，在供应商发布事务中用 `effective` 状态回查。现有代数索引只覆盖 `pending`；OPS 留存的等价谓词只读执行计划为顺序扫描，表约 39.6 万行，堆约 175 MiB。一次采样的累计 I/O 增量无法归到单条 SQL，也未复原与公网 503 的请求级因果关系。

详情和撤回各自在按来源、挂牌、代数和 `pending` 定位的一次更新中写入结果及生效时间。保留原公开资格、改价与撤回判定，重复处理和历史终态不重新赋时。0039 前的迁移历史保持 `unknown`，现有异常的终态空时间留待独立核实。保留唯一 worker、撤回优先、增量接收、每日 CSV、报告和归档调度。

隔离 PostgreSQL 18.6 使用 12,002 个合成事件执行新旧计划。旧补写无候选时顺序检查全部 12,002 行并访问 187 个共享缓冲块；新详情无候选时走现有 `external_full_event_generation` 并访问 1 块，待处理详情和撤回各自同样使用该索引。本次仅验证缓冲访问和计划，没有将合成结果换算为生产吞吐或时延。生产未建索引、停任务或重放请求。
