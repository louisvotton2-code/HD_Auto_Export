## 容量验收矩阵

1. 先确认查询正确性，再依次加载 10 万和 50 万两档。各档包括无筛选列表／facet、常用品牌车型＋价格／年款／能源、低命中搜索、深页与跨流边界。BE 提供精确计数及少量稳定样本 ID。详情、图片上报和真实 CDN 延迟不混进列表／facet 的门槛。
2. 每档分别观察 SQL 原始计划、应用无缓存、Redis 冷填充、Redis 热命中。冷缓存使用新的隔离版本／命名空间，不清空共享缓存。对 20／50／100 并发用固定请求分布做多轮，记录每条路由成功 P50／P95／P99、请求数、HTTP 状态、连接错误、缓存命中／回源次数、PG 连接池等待、CPU／内存／磁盘和 worker 队列情况。记录时间窗口、实际并发、镜像／源码、资源上限及数据种子，以便复跑。
3. 分开跑真实代理防护和隔离查询饱和。真实代理保留现有访客限流，429 单列。查询饱和需 BE 提供仅隔离可用的测量入口或按明确来源身份及预算节流的驱动，选择前不把大量 429 的 P95 当容量。初始门槛按 PM 约定为 20 并发时常用列表及筛选每路由 P95 ≤800 ms、全量非 2xx 和连接失败 <1%；50／100 记录退化和饱和点。
4. 容量环境用合成数据和假供应商。worker 启停期间验证 API 可读性、去重与重放；备份前暂停 API 和 worker 写入，在另一隔离实例恢复后复验数据库、媒体和检查点。预留 worker 预算为 0.5 CPU／512 MiB，实际测得后再评估。
