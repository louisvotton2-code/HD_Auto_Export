# BE-PUBLIC-SEARCH 生产超时复核

固定 BE 工作树 `codex/be-search-production-io`，基线为已发布 v1.0.23 的 `1cca434472a808e2bb16b655ff6242db8af6bea2`。

## 线上证据

- OPS 切换冒烟的两个关键词查询均返回 200 和精确总数 4,347。随后列表 `9c2cf1ee-af84-4d1d-bb29-9144ac01f5de` 与筛选 `217ac161-a122-44a5-95bb-9ec57e7a304d` 均返回 503。API 约 3,003 ms，原因均为 `deadline`。日志记录时回源队列、版本读取、连接池等待和版本重试均为 0。旧版本日志未记录这两个关键词请求的内部阶段。
- 活动生产 API 镜像与已发版本一致。真实数据库约 47.6 万筛选行、115.1 万语言搜索行，搜索表约 19.7 万死元组。已有三语共用的 GIN 索引有效，大小约 324 MiB。中文查询的列表匹配与筛选输入都选择 BitmapAnd，把三元组索引候选约 1.16 万与语言索引候选约 37.9 万取交集。这些是只读 EXPLAIN 的估算。
- 生产 PostgreSQL 实际限制 2 核、1152 MiB，`shared_buffers=192MB`、`work_mem=4MB`。生产 I/O 计时未开启。现场核对仅取元数据和预估计划，两次 503 使用 OPS 已保存的请求和日志。

## 修复范围

供应商投影 UPSERT 经常在价格等其他字段变化时仍写入 `facts`、`localized`。原搜索触发器给已存在的每种语言无条件更新一行。生产搜索表累计约 305.9 万次 UPDATE，车辆目录约 102.0 万次。迁移 `0036` 在结果相同的情况下跳过搜索写入，保留实际文本、标签和语言集合变化的更新。只替换一段函数，保留表结构、索引、三个语言及筛选口径。

`0037` 增加中文部分 GIN，保留全语言 GIN。搜索列表与筛选在 5xx 和至少 750 ms 的成功请求中记录固定阶段和耗时，可区分缓存查询或共享等待、版本、员工和供应商查库、结果生成、缓存校验及响应阶段。日志仅记录固定标签和时长，继续使用原 3 秒期限和公开响应结构。

## 同规模隔离验证

- 50 万条合成车源，中文关键词匹配 4,347 条。与生产相同的 2 核、1152 MiB 容器及数据库内存参数下，旧 GIN 搭配语言索引的实际扫描约 50.3 万条语言索引项。使用中文部分索引后只取该索引的 4,347 条候选，测试计划跳过 BitmapAnd。迁移 `0036` 已生效时，两条热态 SQL 的 `EXPLAIN ANALYZE` 分别约 34.9→11.8 ms 和 34.9→12.5 ms。
- 同规模的 1,000 行价格更新在原触发器下改写 3,000 条搜索行，`0036` 后为 0 条。在并行关键词列表、概览和合成更新的 4 轮观察中，新索引阶段两条 SQL 仍返回 4,347。隔离索引最终约 44 MiB。真实生产盘、冷读和并发流量下的延迟仍需同版验收。
- 从仅登记到 `0035` 的大样本正常升级并复查精确总数和实际被选中的索引。人为在隔离库阻塞搜索表后复现两个 503，列表标记 `supplier_page`，筛选标记 `supplier_facets`，慢成功请求进入独立的 `response`。
- 从 `0035` 起走实际并发预建与迁移流程。缺失、错误定义和真实取消构建残留的无效索引均拒绝登记，数据库保留 `0035` 及原触发器。确认无活跃构建后移除本次无效索引并重建成功。在另一个会话持有写锁时接管耗时约 11 ms，`0037` 正常登记，重跑后索引 OID、物理文件和单条账本记录均保持。
- 最终隔离目录、缓存与报价回归 39 项通过。API 类型检查、构建和 OpenAPI 生成通过。独立复核通过，已修正缓存完成后响应阶段的计时归类。

## OPS 上线交接

1. 用当前保护策略核对数据库、WAL 和实际 PostgreSQL 临时表空间的盘位与余量，同步核对备份或大型同步任务。现场只读观察中数据和 WAL 盘使用约 41%、可用约 229 GiB，容器 `/tmp` 所在盘使用约 66%、可用约 22.8 GiB。这是不含并发构建峰值的快照；隔离索引尺寸供估算，现场需给构建临时文件及 WAL 留空间。
2. 现有生产库使用迁移角色，先检查目标名的定义和状态。名称不存在时，以单一 `psql` 会话、自动提交执行下面三条命令。若用 `psql -c`，每条各用一个 `-c`。

   ```sql
   SET lock_timeout = '5s';
   SET statement_timeout = '90s';
   CREATE INDEX CONCURRENTLY external_catalog_search_zh_trgm_idx
   ON public.external_catalog_search USING gin (search_document gin_trgm_ops)
   WHERE locale = 'zh';
   ```

3. 已存在的索引用 `pg_index.indisvalid`、`indisready`、`indislive` 和 `pg_get_indexdef` 核对。目标必须在 `public.external_catalog_search` 上，定义与上面的中文部分 GIN 完全一致。有效且匹配则直接登记。构建失败或中断后，只有在确认该对象正是本轮留下的同定义无效索引、`pg_stat_progress_create_index` 已无对应构建且无另一个维护者操作时，才在自动提交下执行 `DROP INDEX CONCURRENTLY public.external_catalog_search_zh_trgm_idx` 再预建。发现其他定义时停止并核对。
4. 并发预建完成后按正常发布流程运行迁移服务，保留现有连接选项并向该进程的 `PGOPTIONS` 追加 `-c hd.require_prebuilt_search_zh_index=on`。0037 在此模式下要求索引已经存在，并且只有定义和三个状态精确匹配才通过。无需重复建索引。正常 Drizzle 事务登记 0036、0037，失败保持迁移账本原状。空白库和本机隔离流程仍可用默认迁移模式创建索引。
5. 核对账本、两条查询的真实库预估计划、实际服务镜像和唯一 worker 检查点。发布后用少量现有关键词请求核对 200、精确总数、gzip 和阶段日志，并用正常流量观察超时。旧 API 和 worker 可使用迁移后数据库。应用回退可保留最新数据及迁移，索引本身的变更由 OPS 单独处理。
