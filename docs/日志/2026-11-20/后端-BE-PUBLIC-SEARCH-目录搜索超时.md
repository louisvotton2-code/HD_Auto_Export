# BE-PUBLIC-SEARCH 目录搜索超时

固定工作树 `codex/be-search-timeout`。最初开发基线 `7df53e4c730cac80de85665d3aaa844ad5a9bb61`，冻结于主线基线 `14cd6a5c5809b1b10c9033900ddb6b1a864e0975`。两基线之间是 OPS 的媒体启动兼容改动。范围为公开车辆列表和筛选统计算法，使用已有 PostgreSQL 搜索索引。

## 现场证据

- 北京时间 13:52 绕过本机代理发出两条 `q=马自达` 请求。列表返回 503，公网耗时 4.56 秒，对应请求 `96a472b4-1c40-4e96-b84e-fdb3f2a46af8`。活动 API 为 v1.0.20，日志记录 `catalogReason=deadline`、3,001 ms、回源队列和连接池等待均为 0。
- `catalog-facets.json` 转发到同一 API 的 `vehicle-filters?projection=overview`。同批的筛选返回 200、gzip，公网耗时 4.22 秒，API 耗时 2,416 ms。此前筛选 503 的请求日志未关联到本批探测。
- 生产只读预估计划中，列表总数和取页都从三元组索引匹配关键词，并与语言和可见性结合。统计估算约 47 万条供应商筛选记录、115 万条多语搜索记录。预估计划用于确认索引和访问路径，未执行生产 `EXPLAIN ANALYZE`。故障时单条 SQL 的耗时未被旧日志记录。

## 改动与验证

- 最新排序的卡片首屏在同一数据库快照用一次供应商匹配结果计算精确总数并选取当前页，之后只读取本页展示字段。命中最多物化 8,193 条。一旦超过 8,192 条，使用常规有序取页与完整计数。单字符搜索、深页、游标和车源咨询号沿用原有路径。
- 普通字面关键词直接用按换行分隔的索引文本，列表和筛选共享相同匹配条件。内含换行时仍逐字段核对，避免跨字段误匹配。保留原有语言、上下架口径、员工车优先、价格范围、售价换算和精确总数。
- 10 万条合成目录，交错执行旧查询和新查询并核对精确结果。4,000 条命中的「马自达」列表总数和取页中位数由 28.7 ms 降到 11.7 ms，筛选概览由 16.5 ms 降到 10.4 ms。99,000 条命中的宽搜索返回完整数量及同顺序首屏。覆盖零命中与广泛命中的单字符搜索。
- 隔离 PostgreSQL 中并行执行 8 次价格提交和 8 组列表／筛选请求，16 次全部返回 200。每组的列表和筛选精确总数一致。最终隔离集成 37 项通过，API 类型检查、构建、OpenAPI、workspace 边界及公开列表与筛选的 gzip 协商通过。
- 初次集成测试暴露了合并查询与游标 SQL 的拼接问题。收窄至最新卡片首屏后，隔离回归验证首屏合并、员工车填满首屏、零命中、越界页、跨流游标、有换行的字面匹配、三语与撤回。独立只读审查确认上限与回退范围，无未解决的 P0 或 P1。
