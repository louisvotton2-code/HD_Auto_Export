## 方案与决定

- 将“长期一仓一应用”的推荐调整为“单仓多应用候选”；统一 Git 仓库与各端独立构建／部署可以同时成立。
- 候选正文只维护在 [模块维护的仓库边界](../../开发/模块维护.md#仓库与目录边界)，未新增重复架构文档。七类职责保留，建议三个应用归 `apps/`，公共代码归 `packages/`；扁平七个一级目录也可实现相同包边界。
- 明确每应用独立依赖声明、构建／测试与环境配置，全仓一份锁文件；API 独占数据库与业务权限，官网 SSR 和后台均通过 HTTP API 获取数据；禁止跨应用导入内部源码。
- 公共包优先契约和真正纯粹的计算核心，页面、翻译和数据库逻辑不一并抽出；接口／公共包变化仍需兼容与消费者检查，目录不是安全权限隔离。
- 官网保留 Next；后台候选 React＋Vite 静态构建；API 框架尚未选型。单台服务器仍可承载多个应用，未承诺当前预算或配置已经过容量验证。
- 旧路线图 D-02 标记待修订；BE 的 Next 内业务 API、AD 的官网子路由挂载、OPS 的单 Next 容器图，以及直接调用后端服务的 SSR 路径需要在实施前统一换版。G1 单车闭环与后续阶段顺序保持。
- 先安全保存共同基线，再单独搬官网并回归，再建立契约与后台/API并联调；未创建任何空模块或新仓库。
