# FE-ANALYTICS-RETRY 行为重投与咨询归因

基线为 v2.0.24 `32c4f45e5026d2b1ba393a79e3d4685abf771d3a`。在原有可用的隔离工作树切到 `codex/fe-analytics-retry-attribution`，固定前端工作树的旧编辑、预览和其他候选保留。没有改 API、后台、生产配置、车辆推广开关或访客同意规则。

## 官网修正

- 站内 `/api/v1/analytics/events` 普通批次收到 HTTP 503 后，在原授权内用相同序列化请求体、事件 ID 和发生时间在内存重投一次。等待为 1–1.25 秒，有效 `Retry-After` 最多等 3 秒，超过跳过，503 后 4 秒作废。其他失败保持尽力一次。页面离开取消尚未执行的重投，撤回取消所有待发并中止在途；同意前的事件不会补发，重新同意不会恢复旧批次。
- 真实点击通用页脚、头部或全站咨询弹窗的 WhatsApp／Telegram，仅在已同意时记全站 `contact_click`，不附车辆 ID。打开弹窗仍不计数。车辆卡片与详情明确绑定 ID 的链接保持原来的独立联系计数，详情符合推广资格时保持每个真实渠道点击一次 Meta `Contact`。两条独立发送不会随站内批次重投。

## 后端与 PM 集成

`POST /api/v1/analytics/events` 的既有契约不变。后端的 `analytics_event_receipts` 按 `event_id` 去重 168 小时。回执、车辆日计数和会话及小时更新使用同一个事务。第一次结果未返回但事务已提交时，原体重投不增浏览、联系或漏斗；第一次事务回滚时，原体重投仍可入账。本站 `contact_click` 的 `vehicleId` 已可选，无 ID 的联系只进入全站和渠道汇总。现有匿名计数没有事件 ID，继续只发送一次。

BE／QA 同版验证复用已有 PostgreSQL 并发重投测试，再用隔离网关分别模拟「未入账 503」和「入账后回包 503」；两种情况下，站内事件、详情排行和会话最终均应各写一条，通用联系不进车辆排行。明确区分浏览器已尝试取消和已写入服务端。正式 Meta 实收、生产报表与部署未作为本轮前端验证。

## 验证

- 官网生产模式构建通过。行为发送、统一同意和 Pixel 共 39 项定向单测通过。覆盖同体重投、持续 503 停止、响应指定等待、过期、429、网络失败、跨标签撤回、主动撤回及 `pagehide`。
- Chrome 启用模拟像素配置时 38 项通过，关闭态专用用例另跑通过。对持续 503 的车辆咨询截获两个逐字节相同的站内批次、一次独立车辆计数和一次模拟 Meta `Contact`，只打开一个联系入口。页脚和全站弹窗的通用 WhatsApp／Telegram 保留跳转，站内记录无车辆 ID，未产生车辆计数或 Meta `Contact`。三语提示与同意状态回归通过。未向生产、Meta 或客户发送统计及联系。
- 独立审查复核后端既有事务去重、页面离开、撤回与重投的并行顺序。根据审查建议，首次发送也重读跨标签已保存的选择，等待过久的重投作废，补齐两个反例。没有遗留 P0／P1。
