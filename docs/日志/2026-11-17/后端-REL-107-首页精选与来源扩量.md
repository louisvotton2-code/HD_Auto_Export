## OPS 扩量步骤

1. 先部署 `0031` 与匹配的正式 worker、宿主容量测量程序。迁移后默认仍为 **150,000** 个累计来源身份，运行旧容量裁决的目标保持有效边界。确认单一 `continuous` worker、供应商当日额度和现行日备份。固定范围导入保持关闭。原始资料、三语采集、照片链接、撤回顺序、去重和人工覆盖继续使用现行流水线。
2. 在现行上限下取得最新完整验证的 CSV，确认归档存在、解压后的字节和 SHA-256 与保存的元数据一致，并确认暂存未被裁剪。基于最新上游快照与已收到增量，区分累计准入数、活跃身份和公开去重数。用下列只读查询取得候选累计上限，检查 `stage_rows=rows` 且活跃快照完整。已在历史上占用席位的身份留在累计数中。

   ```sql
   WITH latest AS (
     SELECT id, generated_at, rows, sha256, bytes
     FROM external_full_snapshots
     WHERE state IN ('verified', 'applying', 'complete') AND archive_pruned_at IS NULL
     ORDER BY created_at DESC, id DESC LIMIT 1
   )
   SELECT s.id, s.generated_at, s.rows, s.sha256, s.bytes, a.admitted_count,
          a.admission_limit, x.stage_rows, a.admitted_count + x.new_rows AS candidate_limit
   FROM latest s CROSS JOIN external_formal_admission_state a
   CROSS JOIN LATERAL (
     SELECT count(*) AS stage_rows,
       count(*) FILTER (WHERE ad.source IS NULL AND w.source IS NULL) AS new_rows
     FROM external_full_stage t
     LEFT JOIN external_formal_admissions ad USING (source, external_id)
     LEFT JOIN external_ingestion_identity_state w
       ON w.source=t.source AND w.external_id=t.external_id AND w.provider='chinacarapi'
       AND w.withdrawn AND w.business_at>=s.generated_at
     WHERE t.snapshot_id=s.id
   ) x WHERE a.id=1;
   ```

3. 在修改上限前，使用只读取得的当次实盘、业务、原文、备份和测量样本，在内存中以候选目标调用既有 `capacity-measure.py::project()` 试算峰值。试算不写容量裁决，正式裁决仅在 worker 绑定新目标后产生。保留 70% 实盘和预测峰值停线、有效期、同快照及样本摘要绑定、既有备份预留和运营额度。2026-11-16 的生产对照曾估算完整目标为 459,009 个累计身份，约 392.7 GiB 文件系统在 200,000 目标时已估到 76.4%。现盘能否容纳全目录须以当次实测决定。容量不足时先扩可用盘，或先选择更小的有限阶段目标并重新计算；准备操作只能提高上限。[历史测量](../2026-11-16/运维-数据盘-同步容量与全量估算.md)
4. 停止当前 worker 容器并等生命周期锁释放，确认日备份租约和暂存清理安静。由数据库运维权限在实际 release 库执行 `SELECT prepare_external_formal_expansion(:'snapshot_id'::uuid, :target_rows::bigint);`，使用上一步确认的有限 `target_rows`。该函数复查最新快照、完整暂存、排除撤回和并发锁，事务内保留增量游标并重开该快照的应用进度，设置 `capacity_pending=true`。函数检查上限最多 1,000,000，这个边界不是建议运行值。
5. 将宿主私有 `admissionTargetRows` 设为同一目标，启动匹配版本的单一 worker，让其产生新 `targetRows/snapshotId/evidenceHash`。确认新裁决绑定，`currentUsedBytes` 和 `projectedPeakBytes` 均处于守门线内，且 `capacity_pending` 经常规流程解除。超过 150,000 的新增身份仅由核过实时磁盘和裁决的正式 worker 准入。活跃 CSV 先处理在本次清单中的身份，同一快照内的别名才可占用新席位，已准入的别名仍可关联。未占满后的增量与 CSV 共用席位。已准入身份的撤回和更新保留现有处理方式。
6. 记录累计准入、活跃三语待处理、原文和照片数据、报告队列与现有覆盖抽检，分别核对快照完成和后续增量的新活跃身份。此前因上限而跳过的身份用当前及后续快照重新核验，保留已处理的增量水位。异常时走现有暂停流程，保留已落库的记录与回退证据。应用回退后继续暂停扩量 worker，使用支持新版准入的 worker 和匹配宿主脚本恢复。

## 定向验证

- 一次性 PostgreSQL 18.6 上，首页挂牌生命周期、示例限制与回收站 4 项通过。公开首页与内部 SSR 缓存版本随售出变化，首页显示当前已售状态，目录仍排除售出项。准入与同步相关 22 项通过，覆盖迁移默认值、完整暂存、worker 和备份并发锁、旧裁决停留、别名配额、CSV 与增量共用上限及断点续跑。另复用公开缓存套件中的 8 项通过结果。
- API 容量裁决单测、类型检查、OpenAPI、钩子及差异检查通过。macOS 上两项 Linux 文件系统／root 专用测试有环境差异，改用无网络隔离 Linux 镜像后容量测量与裁决 23 项通过。
- 独立只读审查确认首页资格、公开缓存和既有权限。扩量审查发现快照外别名可提前占用席位，已补校验和回归并复查。待合成验收 AD 候选列表与 FE 库存标签；本轮源码与迁移停留在 BE 工作树，尚无生产扩量裁决或执行结果。
