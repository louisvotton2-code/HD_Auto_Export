# 验证与交接

当前阶段见 [开发进度](../../../../docs/开发进度.md)，本角色任务与证据从 [接手导航](../../../../docs/README.md) 定位，提交规则见 [CONTRIBUTING](../../../../.github/CONTRIBUTING.md)。以下是检查方法，不是已通过结果。

## 验证顺序

1. 阅读相关实现与现有测试，按真实行为选最小足够范围。公共接口／算法需要有辨别力的单测，交互需要真实浏览器；不要为简单文案写与实现逐字对应的测试。
2. 按影响范围运行类型、公共依赖边界与必要单元检查；修改计算契约或规则时保留金额、阈值、缺失状态及说明／复制同步回归。
3. 当前静态阶段先构建最新成品，再运行相关 Playwright 场景；FE-01 官网迁移时改为验证新的生产运行模式。共享导航、页脚或跨页状态改动扩大到相关页面和三语；只有新失败、后续代码变化或未解决风险才重复检查。
4. 看关键截图／真实交互并核对视觉目标。通过测试不等于用户已验收，更不等于官方税法认证、Safari 真机或新服务器已部署。

```sh
pnpm check
pnpm build
pnpm test:e2e
```

命令名称以当前 `package.json` 为准。根 `check` 组合工作区、contracts、API 类型/单元/隔离 PostgreSQL 集成与官网检查；后端检查先按 API README 启动本机测试库。`test:e2e` 仍面向官网构建后的静态预览，定向运行可用 `pnpm --filter @hd/web exec playwright test tests/<相关文件>.spec.ts`。不要复用旧根目录产物；`E2E_BASE_URL` 的测试对象必须明确。

**`next dev`、`next typegen` 与 `next build` 不能并发写同一个应用的 `.next/`。** 先停止本次自己启动的开发进程，顺序执行检查／构建，再恢复预览；不能为清理端口杀掉无关进程。多个 Playwright 进程若并行，分别设置输出目录，避免互相清报告。环境缺运行时或浏览器时先查项目／工具提供的已安装依赖，不盲目换包管理器或锁文件。

重点行为示例：

| 改动 | 检查重点 |
| --- | --- |
| Telegram／WhatsApp 车辆咨询 | 两平台目标账号、解码后的同一草稿、车辆稳定标识／基本参数／详情 URL、三语、特殊字符；不向真实客户发送测试消息 |
| 车卡 hover／3D | 指针沿按钮边缘移动无反复闪烁、链接可点击、离开回正、键盘焦点、触屏及减弱动效 |
| 路由／SEO | 静态文件实际存在、三语及未知 slug、canonical／hreflang、演示 noindex、无 JS 基础路径 |
| 参考算法 | 规则来源与生效期、边界前／等于／后、金额舍入、非法／缺失／待核验、包含和排除费用 |

账号参数和预填格式可验证，不应把 URL 测试写成“Telegram／WhatsApp 已真实送达”。截图、数据来源或公开技术说明如需新增，记录具体页面与观察日期，避免把可变网页内容永久写死在 Skill。

## 文档更新契约

每轮更新自己的角色进度摘要，并按 [统一日志格式](../../../../docs/README.md#每轮如何记录) 新增开发日志；PM 根据这些证据汇总总进度，其他角色无需同时修改。记录：

- 实际完成的能力及主要维护入口。
- 已执行命令、测试目标／数量与真实结果；失败原因与修复后重跑结果分开记录。未执行／未验证明确标注，不能复制上一阶段通过数量。
- 当前限制、未完成任务、下一步可执行动作。
- Git 提交／推送与部署分别发生了什么；未发生的动作不能写成已发布。

相关内容变化再同步对应维护说明：模块／公共入口变动更新模块指南与技术架构；页面或动效改动更新该页面维护文档；税费能力／核验变化更新规则覆盖表；本 Skill 规定的路径／约定改变时一并维护 Skill。不要为凑齐文档修改无关历史记录。

## Git 与部署边界

先看当前用户授权和进度，完成本地可 review 的结果。沿用已给出的提交／推送授权，不重复索要同一许可；若用户规定验收后推送，就遵循该阶段条件。Git 版本记录和服务器发布是两件事。

每轮先 `pnpm hooks:check`，未启用先 `pnpm hooks:install`。自测后主动分派独立 Reviewer，修复复查后保存提交并核对 SHA；按 [推送前检查](../../../../docs/协作/测试与审查.md#推送前检查) 运行 `pnpm verify:push --base <基线SHA>`，登记匹配的真实独立报告后推送。新提交或报告变化会使旧记录不适用；不得自行 `--no-verify`、关闭 hooks 或编造通过记录。新 clone 不继承本地配置，prepare 不是唯一安装保障。

用户不安排另一 GitHub 审核账号；main 必须 PR＋指定来源的 verify 检查，管理员也受限，GitHub 批准数为 0。独立 Agent 审查由本地流程负责；hook 的本地证据不是不可伪造的身份认证，远端也不会据此认证 Agent 审查。

提交前核对仓库根目录与暂存范围：

```sh
git status --short
git diff --check
git diff --cached --stat
git diff --cached --check
```

只包含本站当前任务文件；不覆盖其他 agent 的并行改动，也不顺手整理用户已有文件。凭据、真实环境、数据库、备份、`docs/private/`、依赖与生成产物不得提交。不要在父项目仓库提交本站文件。

当前静态方式托管完整 `apps/web/out/`；后续各端实施后须分别验收与发布产物，不能继续照搬静态模板。是否部署、部署到哪里由本次授权及实际环境决定。若当前进度限定本地验收或新服务器资料尚未提供，不使用历史登录信息连接旧服务器；不能从部署文档推断用户授权已重新启用。后续真实部署先读当时的实际记录，保留现有服务、回滚版本和哈希资源，不重复首次安装或重置 VPN／防火墙。Skill 本身不携带凭据，也不提供生产操作授权。

功能审查、QA、阶段 PM 验收与用户确认使用统一的 [测试与审查流程](../../../../docs/协作/测试与审查.md)。审查与自测分别提供证据，预留包没有业务检查，不把跳过的脚本当作通过。
